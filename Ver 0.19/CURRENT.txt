True MultiExtractTool —— V0.17 开发线（对外报 0.16E）
==================================================

**版本号规则（这一版起，以后都这样）**：开发线在验收通过前，一律报
「上一个已发布版本号 + E」。本目录是 V0.17 开发线，`me/config.py` 里写的是
`0.16E Beta NNNNN`；全部自测与两条通道的验收通过之后，才改成
`0.17 Beta NNNNN`（同时 `python bump.py --release 0.17`）。

本轮第二批：Unreal 自研解析
--------------------------
`me/formats/ue_pak.py`：纯标准库读 `.pak`，不启动任何外部程序。

* 文件尾 `FPakInfo` 用「找魔数 0x5A6F12E1 + 校验索引区间」定位，
  不按版本硬编码尾部长度（实测各版本 44/172/204/205 字节都有）。
* 索引字段宽度不写死：压缩方式 4 字节 / 1 字节、时间戳 0/8 字节等组合
  逐个试，**要求恰好读完整个索引**才认。同一版本号下 repak 就写出两种长度
  （V8A 1 字节、V8B 4 字节），真实 UE 也不保证只有一种。
* 未压缩条目的数据在「条目偏移 + FPakEntry 头」之后，按版本算出头长；
  压缩条目走块表，版本 5 起块偏移是相对条目起点的（加回偏移）——
  这两条都是实测出来的，写错就会被解成别的文件的字节。
* 压缩只解 zlib / gzip（标准库）；Oodle / Zstd / LZ4 明确报「解不了」并计数。
* UE5 的 v10/v11（多层索引 + 位压缩条目）还没做：遇到抛
  `UnsupportedVersion`，引擎把这条 pak 交回 repak，notes 里写明白。

对照证据：`selftest/test_ue_pak.py`（24 项）—— 手写合成 pak（含 UTF-16 文件名）、
畸形文件、v10/v11 报错，以及**真 repak 打包的 17 组样本**（V0–V9 × 未压缩/
zlib/gzip）条目名与 repak list 完全一致、解出的字节与源文件逐字节相同。
`selftest/test_unity_unreal.py` 另加 E3：同一个 pak 走 `ctx.channel="self"`，
4 个文件全部逐字节一致。

本轮第三批：Enigma 自研解析
--------------------------
`me/formats/evb.py`：只读 `.enigma1` 节里的虚拟文件系统，不启动 evbunpack。

* PE 解析找 `.enigma1`；记录按「名字 UTF-16 + 名字后 58 字节固定字段」走，
  下一条名字 = 本条名字 + 名字字节数 + 70。
* 字段顺序全是从字节里量出来的：类型在名字后第 0 字节、原始长度第 3 字节、
  属性（u32）第 35 字节、存储长度第 50 字节；数据从最后一条记录的结束处开始，
  按记录顺序紧密排列。
* 压缩条目（存储长度 < 原始长度）按 LZMA 解，ALONE / RAW 两种都试。
* **不做 PE 还原**：把原始 exe 拼回来对抽资源没用，这部分留给第三方。
* 表结构与已知版本不符时抛 `EvbError`，引擎退回 evbunpack —— 不猜。

对照证据：`selftest/test_evb.py`（26 项）—— 手写 PE + `.enigma1`（含目录节点、
LZMA 压缩条目）往返，畸形文件四个用例，真样本 4 个条目 / 数据起点 0x783525，
以及引擎端到端（`--only text`，channel=self，内层也继承自研）。
真样本的 4 个文件与 evbunpack 的产物**逐字节相同**（data.win 63,630,288 字节）。

第四批：Unity 调研（未写解析器，只把地形摸清）
--------------------------------------------
本机唯一的 Unity 样本：`桌面\02_游戏开发\Unity解包资源\PapersPlease解包\`
（Unity 2022.3.62f2）。现状与结论：

* 文件不是标准 SerializedFile 头。实测各字段（大端）：
  `+0x08 version=22`、`+0x14 meta_size`、`+0x18 file_size(i64)`、
  `+0x20 data_offset(i64)`、`+0x30 "2022.3.62f2\0"`。
  三个文件的 `data_offset - meta_size` 分别是 61/62/63，只有把元数据起点
  取成 61 再对 16 取整才同时成立（1008 / 1248 / 3408）。
* 元数据里**没有类型树**（`m_Width`、`Texture2D` 这类字符串一个都搜不到），
  也就是说即使解出对象表，也需要内置类库才能把字节映射成字段 —— 这是
  Unity 自研的真正难点，不是「解不开容器」。
* 试过 4 种元数据起点 × 25 种类型条目长度 × 2 种对象条目宽度 × 有无 big_id
  的组合暴力搜索，要求「解析正好吃掉 meta_size 且所有对象区间落在数据区」，
  三份样本全部无解 → 说明这个容器的元数据段与标准布局不同（很可能是
  某个「一键解包」工具重写过的容器，或另有包装）。
* 对照组有了：AssetStudio（第三方通道）能读这些文件，单文件跑一次导出
  185 个对象（MonoBehaviour / Mesh / Texture2D / AudioClip），
  所以「自研读出来的东西对不对」有现成的比对基准。
* 数据侧线索：`sharedassets0.assets` = `sharedassets0.assets.split0..3`
  按 1MB 拼起来（1MB×3 + 195,680 = 3,341,408 字节，正好相等），
  这些 1MB 块像是按 UnityFS 块大小切过又被工具拼回去的。

下一步（下一轮从这里接）：
1. 先确认这个容器到底是标准 SerializedFile 的哪种变体：拿一份**未被动过**的
   Unity 文件（另一款 Unity 游戏，或自己构造一份 v22 标准样本）做对照；
2. 若确属第三方工具重写的容器 → 自研通道对它明确报「未覆盖」并退回
   AssetStudio，同时把「标准 SerializedFile（带类型树）+ UnityFS 包」这条
   主线按合成样本实现并验证（类型树在编辑器构建/部分游戏里是有的）；
3. 若确实是标准布局、只是我读错了字段顺序 → 按对象表 → m_Name/Texture2D
   字段推进，最终目标仍是 Texture2D/AudioClip/TextAsset 三类。

第五批：Unity 找到真样本，先落 LZ4
--------------------------------
两条新线索（本机实测）：

* **两份未被改过的 Unity 游戏**（Steam 安装目录）：
  `Goose Goose Duck_Data\data.unity3d`（737 MB，Unity 6000.0.71f1）、
  `SurroundedByBoys_Data\data.unity3d`（44.8 MB，Unity 2022.3.55f1c1）。
  两个都是标准 **UnityFS** 包（`UnityFS\0` + 版本 8 + `5.x.x` + 版本串）。
* 新增 `me/formats/lz4_block.py`：纯标准库的 LZ4 **块**解压（UnityFS 的块与
  块信息都用它，标准库没有 lz4）。`selftest/test_lz4_block.py` 14 项：
  纯字面量、15/20 字节扩展长度、offset=2 匹配、offset=1 重叠复制、
  长匹配扩展、expected_size 校验、5 种坏数据必须报错。

实测（两份真包）：

| 包 | 块信息压缩后 | 解压后 | 结果 |
|---|---|---|---|
| Goose Goose Duck | 80,203 | 222,313 | 字节数完全吻合 |
| SurroundedByBoys | 5,317 | 14,047 | 字节数完全吻合 |

解压出来的块信息里已经能看到目录项名字：`globalgamemanagers`、`level0`、
`resources.assets`、`sharedassets0.assets`、`*.resS` —— 也就是说
UnityFS 的「块表 + 文件目录」是同一块数据，下一轮从这里接着解析。

顺带纠正上一轮的判断：UnityFS 的块信息**不在文件尾**（flags 里 0x40 位
不能按字面理解），实测在「头对齐到 16 之后」的 64 字节处。

第五批续：块表/目录仍未定标（下一代接着做）
------------------------------------------
已确认：
* 块信息解压后的字节数 = 头里的 `ubinfo`（14,047 / 222,313），两份包都对得上
  → LZ4 块解压实现可用。
* 解压出来的内容里确实有文件名（`globalgamemanagers`、`level0`、
  `resources.assets`、`sharedassets0.assets`、`*.resS`），文件名在信息区尾部。

还没定标：
* 块表：块记录看起来是 10 字节 `[u32 未压缩][u32 压缩][u16 flags]`（尾部
  实测到 `131072 / 40771 / 3` 这样的干净三元组，周期正好 10），但用
  「u32 块数在偏移 16、块表从 20 开始」去解第一块就对不上
  （`u=512, c=0xd7200100`）。说明块表起点不是 20，块表前面还有别的字段。
* 目录：`[i64 偏移][i64 尺寸][u32 flags][名字\0][4 字节对齐]` 这个假设在
  两份包上都验证失败（按名字位置反推 20 字节，读出来是垃圾）。
  名字前面那段是 `… 00 01 af 82 00 00 00 00 00 09 01 b4 40 …`，看不出
  i64/i64/u32 的分界。

下一轮做法（不猜）：
1. 用 AssetStudio 读同一个包，拿到它认为的**文件清单和每个文件的偏移/尺寸**，
   当作基准去对齐信息区里的字段；
2. 两份包（44MB / 737MB，Unity 2022.3 与 6000.0）交叉验证同一条布局；
3. 定标后先只做「解出包内文件」这一件事（SerializedFile 不动），
   解出来的 `globalgamemanagers` 再拿去重做上一轮没搞定的元数据定标。

第六批：UnityFS 索引定标成功
--------------------------
`me/formats/unityfs.py`：头 + 块表 + 目录全部定标，两份真包都验证过。

| 包 | 块数 | 文件数 | 载荷 | 结果 |
|---|---|---|---|---|
| SurroundedByBoys（Unity 2022.3.55） | 1,369 | 8 | 171.1 MB | 索引全部自洽 |
| Goose Goose Duck（Unity 6000.0.71） | 21,969 | 67 | 2,746.0 MB | 索引全部自洽 |

关键修正（都是实测出来的）：
* 块表和目录是**大端**，之前按小端读所以全是垃圾；块信息本身也是大端。
* 块信息在**头部对齐到 16 之后**（不是文件尾）。
* 块信息开头有 **16 个零字节**，块数从第 16 字节开始数。
* 目录条目 = `i64 偏移 + i64 大小 + u32 flags + 名字 + NUL`，**名字后不补齐**；
  之前按 4 字节对齐算，第二个文件的名字就少两个字符。

`selftest/test_unityfs.py`（23 项）：手写不压缩包（含跨块文件）往返、
node 越界/非 UnityFS 报错、两份真包索引断言。

**还没解决**：载荷解压。两份包的块信息是标准 LZ4（解得开、字节数正好），
但**块数据不是 LZ4** —— flags 写的是 3（LZ4HC），实测每个块都解不开
（`匹配偏移为 0`），块 0 的内容甚至直接是 SerializedFile 头（版本 22、
后面跟着 "2022.3.55f1c1"）。游戏目录里也没有 `oo2core_*.dll`。
下一轮先判定载荷编码：拿块 0 的字节按「不压缩」假设去核对 node0 的
227,204 字节（若头/字符串/尾部都自洽，说明这批包的载荷就是明文，
块表那个「压缩长度」是别的含义）。

第七批：载荷编码排查（仍未定标）
------------------------------
先把能确定的钉死：

* 块的**文件布局是对的**：`data_offset + Σ(compressed) = 44,827,839`，
  文件总长 44,833,231，差 11 字节（尾部对齐填充）。
  也就是说块 0..n-1 确实按顺序紧挨着放在 `data_offset` 之后。
* 块 0（`@5381`，73943 字节）开头是 `00×11 16 00 01 00 16 …`，
  +36 字节处就是 `"2022.3.55f1c1"` —— 这是 node0
  （`globalgamemanagers`）的 SerializedFile 头。
* 按 LZ4 解：所有块都失败（首字节 token=0 时偏移字段为 0，格式上非法）。
* 按 LZMA（外层 5 字节 props，首字节应是 0x5D）解：块首字节是
  0x00 / 0x03 / 0x7c，都不是。
* AssetStudio 只有 Lz4 和 Lzma 两种实现（DLL 里只有这两组符号），
  但它能读这份包并导出 2,479 个资源 → 要么它走的不是块解压路径，
  要么载荷真是这两者之一而我的起始偏移还差一点。

下一轮：先把「AssetStudio 到底读的是不是这个包」确认清楚
（把 data.unity3d 单独拷到一个空目录再跑，看导出数量与日志），
再决定是继续啃 LZ4 的变体，还是把载荷当明文去对 node0 的 227,204 字节。

第八批：载荷编码排查（第二轮，仍无解）
------------------------------------
* 已确认 AssetStudio 读的就是这个包：把 `data.unity3d` 单独拷进空目录，
  它报 `Detected Unity version from data.unity3d: 2022.3.55f1c1`、
  `Loading ...\data.unity3d`、导出 286 个文件（956 个资源对象）。
  而它的 DLL 里只有 Lz4 / Lzma 两组符号 → 载荷必是这两者之一。
* 暴力对齐也没命中：以 `data_offset=5381` 为基准，
  起点扫 ±4096 字节 × LZ4/LZMA（LZMA 还试了 props 推导的 lc/lp/pb 与
  4 种字典大小），判据是「解出正好 131,072 字节且开头是
  `…00 16` + 版本串」，命中 0。
* 又试了「前 N 字节明文 + 其后压缩」的前缀假设（N = 256…65536），LZ4 也
  全部不成立。
* 反向（块倒序）也扫过 4096 个起点，命中 0。
* 反面证据：块数据在 `@5381` 直接就是 `00×11 16 00 01 00 16 …` 加
  `"2022.3.55f1c1"`，而块布局的算术又严格吻合
  （`Σ compressed = 44,827,839`，文件长 44,833,231，差 11 字节尾部填充）。
  也就是说「边界对、内容看着像明文」，但「当明文用」又装不下
  （节点总长 179,385,920 字节）。

结论：这个包的载荷不是我从 5381 起能解开的 LZ4/LZMA。要么块数据前面还有
一层我没识别出的封装（Unity 2022/6000 的新块格式），要么块表的
`uncompressed` 列在别的空间里。下一轮换样本验证：找一款**老版本 Unity**
（2019/2020）的游戏包，如果老包能按现在的代码解开，说明差异在 Unity 版本；
如果老包也解不开，说明我的块起点算法从根上差一层。

第八批续：整段流假设也否掉了
--------------------------
* 把整个数据区（44,827,839 字节）当成**一条连续的 LZ4 流**去解，
  期望解出 179,385,920 字节 —— 首字节就失败（`匹配偏移为 0`）。
  所以不是「块边界切错、流本身连续」这种情况。
* 至此否掉的假设：逐块 LZ4、逐块 LZMA、整段 LZ4、明文前缀 + LZ4、
  块倒序、块表两列互换、载荷整段明文。

唯一还没试的方向：块数据前面可能有**每块 N 字节的私有头**（N 还没定），
或者 Unity 2022/6000 换了块编码（flags=3 的含义变了）。
下一轮按计划换**老版本 Unity** 的包做对照，用版本差异定位。

第九批：补证「载荷确实是压缩的」+ 本机无对照样本
----------------------------------------------
* 用 AssetStudio 从这份包导出 101 个文本类资源，再拿它们的字节回包里搜：
  最长的连续命中只有 16～32 字节（726 字节的 JSON 一段都找不到完整连续）。
  **这直接证明载荷是压缩的**（明文的话整段都会命中）。
* 所以「看着像明文」只是 LZ4 字面量段的错觉，块起点确实不在 5381。
* 又试了 raw LZMA（无 props 头，lc/lp/pb 60 种组合 × 4 种字典）解块 0，
  0 命中。
* 本机找对照样本失败：全盘只有这两款 Unity 游戏（都是 Unity 2022+），
  没有 2019/2020 的老包；也没有 UnityPy / AssetRipper / UABE 之类
  带源码的参考实现（`pip list` 空，磁盘上只有 assetstudio 的二进制）。

**结论（需要外部输入才能继续）**：UnityFS 的「载荷块」这一层，用现有证据
无法定标。要往下走，需要下面任意一项：
1. UnityFS 块格式的规格说明（或 UnityPy/AssetStudio 的源码片段）；
2. 一份**未压缩**或**老版本 Unity** 的 .unity3d 样本（能拿来二分定位偏移）；
3. 一份已知能正确拆开的同款包 + 它拆出来的文件（当对照）。

第十批：UE5 的 pak v10/v11 开始拆结构
----------------------------------
用 repak 生成一份 V11 样本（2 个文件，索引 138 字节）逐字节读出来：

```
+0    FString  mount "../../../"
+14   u32      NumEntries = 2
+18   u64      PathHashSeed = 0
+26   u32      bHasPathHashIndex = 1
+30   i64      PathHashIndexOffset = 0x220
+38   i64      PathHashIndexSize   = 0x20
+46   u8[20]   PathHashIndexHash
+66   u32      bHasFullDirectoryIndex = 1
+70   i64      FullDirectoryIndexOffset = 0x240
+78   i64      FullDirectoryIndexSize   = 0x37
+86   u8[20]   FullDirectoryIndexHash
+106  32 字节  编码后的条目表（位压缩，待解）
```

也就是说 v10+ 的索引是「主索引 + 路径哈希索引 + 完整目录索引」三块，
主索引尾部还有一张位压缩条目表；文件表要跟着 `FullDirectoryIndexOffset`
去读。下一轮按这个骨架实现，用 repak 的 `list` 当基准对齐，
再决定位压缩条目是「必须解」还是「可按目录索引绕开」。

第十批续：V11 的三段索引都读出来了（还没接进解析器）
------------------------------------------------
完整目录索引（FullDirectoryIndex，55 字节）:
```
u32 NumDirs = 2
  u32 目录名长, 名字 "/\0", u32 文件数 = 1
     u32 文件名长, 名字 "a.txt\0", u32 条目号 = 12
  u32 目录名长 = 5, 名字 "Sub/\0", u32 文件数 = 1
     u32 文件名长, 名字 "b.bin\0", u32 条目号 = 0
```
路径哈希索引（32 字节）: `u32 条目数 = 2` + 每条 `u64 路径哈希 + u32 条目号`
（实测条目号 0 与 12，和目录索引里的 12 对上）。

所以 v10+ 的取数据路径是:
`主索引 → FullDirectoryIndexOffset → 目录索引(名字 + 条目号) → 条目号是
「编码条目表」里的**字节偏移**`。主索引尾部那张 32 字节表就是编码条目表,
条目号 0 / 12 分别落在它的第 0 与第 12 字节上。

实测样本里 a.txt 的载荷在 +53（大小 100），b.bin 在 +206（大小 200）,
数据区开头 32 字节是 a.txt 的 FPakEntry 头（`00…00 64 00 00 00 …`）。

下一轮：解编码条目表（位压缩），或者找一个不需要它的路径
（例如直接按 FPakEntry 头 + 目录顺序推算偏移）。两条路都先用 repak 的
`list`/`unpack` 结果做基准。

已交付且可复核的部分（不受此阻塞）：
`me/formats/lz4_block.py`（LZ4 块解压，14 项自测）、
`me/formats/unityfs.py`（头/块表/目录，23 项自测，两份真包索引全对）。

补（0.16E Beta 00088）：默认字体钉回 Microsoft Sans Serif 8.25pt
------------------------------------------------------------------------------
迁移后实测客户区 933x638（设计值 800x450）—— 原因是 .NET 5+ 的

补（0.16E Beta 00089）：没部署过的机器怎么拿到 ini
------------------------------------------------------------------------------
问题：CLIPath.ini 原来是「CLI 每次运行都写」的产物。新机器上如果先双击壳、
或者壳和 CLI 分开放，这台机器根本还没有 ini，壳只能干看着日志报错
（"CLIPath.ini 不存在"），按钮全灰，用户不知道下一步做什么。

改法（Form1）：
  1. 优先级加一条：环境变量 ME_CLI_DIR，显式指定，部署脚本/快捷方式可用。
  2. 全都找不到时，右上角版本标签变成红字「未找到 CLI · 点此定位」，
     点开选目录 → 校验 → 自己写 %LOCALAPPDATA%\MultiExtractor\CLIPath.ini
     → 重新加载版本/分类/引擎，按钮恢复可用。不需要用户手写 ini。
  3. 首次成功定位且 ini 不存在时，壳也主动写一份（存在则绝不覆盖用户改动）。
  4. 校验分两层：
     - PE 头粗检（MZ + PE 签名）。实测过：目录里放个同名文本文件，
       旧逻辑直接拿去启动，Windows 弹「不支持的 16 位应用程序」对话框；
     - 用户手选目录时再试跑一次 --version（退出码 0 且输出含 MultiExtract）。

CLI 侧的既有契约不变：me/cli_path_ini.write() 仍然每次运行都写
CLIPath.ini + version.ini，整包挪盘后壳立刻能拿到新位置；setup.ini 由
setup_ini.ensure() 首次运行生成。所以「CLI 跑过一次」或「壳点一次定位」
任一发生，配置就齐了。

实测（Windows 11 / 96 DPI，均为真启动 + PrintWindow 抓图核对）：
  A 只有壳、无 ini、无 cli\  → 红线提示「未找到 CLI · 点此定位」，按钮灰，
    不写 ini（等用户选择）
  B 无 ini + ME_CLI_DIR 指向真 CLI → 版本显示 0.16E Beta 00089，日志
    「来源: 环境变量 ME_CLI_DIR」「首次运行，已写入 …\CLIPath.ini」
  C 便携 cli\（junction 冒充）、无 ini → 自动写 ini，指向解析后的 CLI 目录
  D ini 已存在 → 壳不覆盖（CLI 自己会按契约重写成本机实际位置）
  E1 假 CLI（文本文件冒充 exe）→ Windows 弹 16 位程序对话框（旧逻辑）
  E2 同上，PE 检查上线后 → 不启动、不弹窗、不写 ini，日志给出
    「ME_CLI_DIR 指向的目录不能用: 不是有效的 Windows 程序（缺 MZ 头）」

文档：README 的「壳定位 CLI 的顺序」改为 4 步并加了 ini 生成时机表；
GUI-API §9 同步。

------------------------------------------------------------------------------
进度条刷屏修复（用户截图：下载 UTMT 时一屏进度条）
------------------------------------------------------------------------------
现象：每帧进度都占一整行，滚了好几屏。
原因：render_progress 把每帧固定补到 120 字符再写 \r。控制台比 120 窄时这一帧
      会折行，\r 只回到**折行后**那一行的行首，于是每次更新都新起一行。
修法（me/ui.py）：
  * 每帧按终端宽度（shutil.get_terminal_size，最少按 40）截断，超长用 … 收尾；
  * 记住上一帧的可见长度，用空格擦掉残影，而不是固定补到 120；
  * 进度条长度随宽度自适应（>=72 列画 20 格，否则 10 格）；
  * 字节数换成 1.5MB/59.7MB 这种短写法，别再写六位小数原值；
  * total 未知时只显示已处理计数，不画百分比；
  * clear_progress 按上一帧长度擦除。
自测（selftest/test_progress.py 加了一段假控制台）：
  宽度 60/80/100/120/200 五种情况，断言「帧内无换行」「每帧不超过终端宽度」
  「收工恰好换行一次」「每帧都从行首覆盖」；另验 total=0 时不写百分比也不换行。

在线更新（Self-Updater）落地：--update + daemon.bat（0.18E Beta 00096 追加）

  ME_UPDATE_URL 覆盖地址；文件见仓库根的 version.json（sha256 是 v0.17R 那个 143.9 MB

二、版本比较（用户指定：只比主版本号）
  parse_version 认 "0.18E Beta 00096" / "v0.17R" / "0.18Rc"；
  compare() 剥离 E / Rc / S / WIP 后缀，只比 X.Y —— 0.18E 与 0.18R 视为同一版，
  不会互相催更新；同一条线要换后缀必须 --update verid=0.18R 明确点名（same_line_better）。
  本机稳定版 + 远端有更高公测版 -> 用「有公测版可用，是否更新？」这句话问。

三、CLI 流程（顺序即协议）
  查清单（3 秒超时，失败只打一行 [warn] 检查更新超时，退出码 0）
  → 比版本 → 确认（-y 跳过）→ 下载 UpdatePack.zip（单行原地刷新进度）
  → SHA256 校验（不一致：报错 + 删文件 + 退出码 70）→ 写 daemon.bat
  → 静默拉起（DETACHED_PROCESS | CREATE_NO_WINDOW）→ 主程序退出释放文件锁。
  事件：update_check / update_ready / update_launch / update_failed /
        update_cancelled / update_pending。

四、daemon.bat（实测出来的两个坑）
  * 等 2 秒用 ping -n 3 而不是 timeout /t 2：detached 拉起没有控制台，
    timeout 直接报 Input redirection is not supported，等于没等；
  * tar 的目标写 "%~dp0."（带点）：%~dp0 自带结尾反斜杠，写成 "...\\" 会把
    引号转义掉，tar 报 could not chdir；
  * 解压失败不删包、不启动；成功才 del 包 + start 新程序；
  * 自删除用 (goto) 2>nul & del "%~f0"，别用嵌套引号的 start /b cmd /c。

五、启动自检（每次启动，第一秒）
  * 有 daemon.bat -> 静默删掉；
  * 有 UpdatePack.zip -> 交互式问「是否立即安装？(Y/N)」；Y = 写 bat + 拉起 + 退出；
    N = 保留。非交互（管道/计划任务/--json）不询问，只发 update_pending 事件。

下工具时进度不动：下载器本来就是 Python 的，缺的是「状态」（用户反馈）
------------------------------------------------------------------------------
现场：GUI 里按「下载工具」，标题变成「工作中（外部工具未回报进度）」，
进度条一直 0。查下来不是下载器的问题 —— me/tools/fetch.py 一直是 Python，
只是**连接阶段一个字节都没有时它什么都不发**：

  * 直连 GitHub 卡住 → urlopen 60 秒超时，这 60 秒 GUI 一条事件都收不到；
  * 一个 256 KB 块在慢镜像上要 3~4 秒才读完，期间也没有 tick。

改法（CLI 侧）：
  * CONNECT_TIMEOUT 60 -> 8 秒：直连卡住时 8 秒就换下一个镜像；
  * 每次尝试开始先 tick(0,0)：事件流里立刻有一条 progress，GUI 知道「在连」；
  * CHUNK 256 KB -> 64 KB：慢镜像下每 1~3 秒就有新读数，不再几秒空白；
  * 每次失败都 log 一行「直连 失败（8.0s）: …」，用户能看出是网络不是死机；
  * 记住上次成功的镜像（last_mirror.txt），下次先试它，不再每次从头等 8 秒；
  * --tools-get 启动时若清单还是「内置兜底」，先等一次远端（3 秒上限），
    否则上游新加的工具永远下不到。

改法（GUI 侧）：
  * progress 里 total<=0（或 total<=1 且 done=0）→ 标题「下载中 连接中」，
    进度条切滚动条，不在 0 上钉死；
  * 下载中看门狗阈值 2 秒 -> 6 秒，超时文案改成「下载中（等待网络数据）」；
  * 任何 progress 事件都重置看门狗（原先 total=0 的事件不算进度）；
  * 标题按 _toolAction 显示「下载中 / 提取中」，字节数用 HumanBytes。

  {"t":"progress",...,"done":262144,...}                    11.8s
直连失败时会打「直连 失败（8.0s）: URLError: timed out」再换 ghfast.top。

V0.19 起线：目标「可反编译出 mfa」（0.18R Beta 00098 -> 0.19WIP Beta 00099）
------------------------------------------------------------------------------
用户指示：「V0.19，目标：可反编译出mfa」。

先摸清了两件事，都记在 ROADMAP 的 V0.19WIP 段里：

  1. MFA 不是 CCN 换个壳。CCN 是 i16 id / i16 flag / i32 size 的 chunk 流；
     MFA 是 MFU2 头 + 工程字符串 + 缩略图 + 四个库 + 应用设置 + 全局值/字符串/事件
     + 帧偏移表 + 各帧 + 帧后的对象 chunk 列表（u8 id + i32 size，id=0 收尾）。
  2. 公开实现里 CTFAK 有 CCN->MFA 的翻译器、NebulaFD 有 MFA 读取器，
     但**两边都没有能用的 MFA 写入器**（NebulaFD 的 Image.ReadMFA 是空函数），
     所以这条只能自己写。

这一轮先把**能逐字节验证的前段**落地：

  新文件 me/formats/ctf25/mfa.py
    * MFU2 头：4B 魔数 + u16 版本 + u16 子版本 + u32 编辑器版本 + u32 构建号 + u32 语言

=== 2026-11-09（第 10 轮 / 0.19WIP Beta 00106）帧数与帧名进来；帧头加密成已知阻塞 ===

这轮目标本来是「拆帧内图层」，结果撞上硬墙，但把墙的位置量清楚了，还顺手拿到
了帧数与帧名。

1）成品的帧名读得出来
   CCN 每帧是一个 0x3333 容器，里面的 0x3335（Frame Name）是**普通 zlib 块**
   （flag=1：头 8 字节 = 解压长度/压缩长度，后面 zlib），实测第一帧名 'start'。
   dtlg-v1.1.0.exe 一共 31 帧。

2）帧头读不出来 —— 是加密块
   0x3334 Frame Header（28 B）：10 00 00 00 之后不是压缩长度，而是
   63 22 c2 23 / e3 27 60 3d / e5 da 22 c3 …；0x3342、0x3341、0x3337 同样。
   直接把 body[8:] 丢给 zlib 报 incorrect header check。
   观察到：同一文件里这几块的头都是 e3 27 开头，而 0x3335 那种普通块没有这种现象
   —— 像是一套固定密钥流的异或。要往下走，得先破这套异或，不猜。

3）转换器：帧数与帧名用成品，其余保持骨架
   mfa_build.read_ccn_frames() 读帧名；build_from_ccn 按它克隆骨架帧、改名、
   句柄重排 0..N-1。报告的 notes 里写明「帧名来自成品；尺寸/背景/图层仍是骨架的」。

   修了 build_project 的一个副作用：全局量段长度随帧数变（每帧 4 字节偏移），
   原来拿旧帧数算长度，导致「帧起点与全局量段尾不接」（差 0x78 = 30×4）。
   现在先用同样条数的占位表量长度，再填真实偏移。
